# 全费用管理交互原型

## 当前入口（2026年11月19日）

[打开交互原型](./原型.html)。沿用原文件和已有浏览器数据。首页是客户列表，选择客户或单据才进入独立详情。

| 我要做什么 | 去哪里 |
| --- | --- |
| 查某客户的销售贡献、返利权益、受益投入及合同 | 客户台账 → 选择客户 |
| 给不同客户配政策、年返时点，制定活动方案或保存试算 | 策略与方案 → 合同政策 / 活动方案 / 费用试算；合同列表的「资金时点与来源」配置真实资金规则 |
| 设资金池、配获取规则、登记签收或退货、发起期间核验 | 资金管理；在总资金池展开「按组织查看分配与占用」 |
| 发起活动、提交核销，或处理等待审批的单据 | 活动与审批 → 活动与核销 / 待审单据 |
| 登记支付、抵扣，或核对未入池和退货差额 | 结算与对账 → 结算与清偿 / 异常与对账 |

策略影响随策略展示，方案采用选择时的快照；独立影响矩阵和模拟流转沙盘已移除。规则说明在页首。客户或活动方案内的结算保留来源范围；需要查其他客户时，显式选择「查看全部结算」。

**当前演示路径：** 策略与方案 → 合同政策 → 资金时点与来源：逐条选择「直接返给客户」或「转入客户余额」，并设置活动额度的释放条件。资金管理 → 销售入池登记有效签收，回到总资金池看「签收行费用分配」。期间结算到期发起核验，业务和财务通过后，在结算与对账登记直接兑现，或选择本客户的订单使用余额。下单试算不记账，活动审批不重复注入资金。

按 100,000 元 × 10% 的样例，扣年返 2,000 元、服务 3,000 元后，剩余 5,000 元才参与解锁和组织分配。返利预留和客户可用余额是两个不同阶段。年度核定与实际付款分开；转余额也不标为现金支出。当年已保存的旧流水不改写。新口径验收见 `qa_order_package.mjs`。

以下为功能迭代记录；旧版本所列入口以本表为准。

## 合同、签收与返利调整（2026年11月18日）

- 在销售费用试算中打开客户 B 的 20 万元方案，可同时查看合同费用 2.4 万元、按获取规则预计入池 2 万元及其规则版本。
- 在销售入池中按合同登记订单。分批交付从首批填写订单数量与签收单行，各批登记本次净额。退货选择具体原签收。
- 在客户资金策略中新增月返，原年返继续累计。费率或阶梯变化可选择全期承接或分段。切换来源池或核验周期会另开统计段。
- 在客户台账选择合同，可查看关联策略、活动方案、销售及每笔资金流水。已有外部批准凭证的独立合同可由财务接入。
- 在结算与清偿进入退货待调整的原批次。业务复核提交冲销申请，财务确认后更新可发放金额。超出未付余额的部分按实际收款凭证登记追偿。

## 全部业务页面适配修订（2026年11月17日）

政策查看、新建与复制、客户活动方案、策略配置、资金池与获取规则、客户资金策略、销售登记、期间核验、活动申请、审核与核销等独立页面统一取消980px/1100px限制，卡片使用主内容区可用宽度。表单依据各自容器宽度显示最多三列，优先保证每个字段280px；手机使用单列，政策四级组织比例保持成组展示。试算左右面板内的字段独立适配，避免因屏幕宽而挤压窄面板。

列表、客户台账、组织池和清偿等页面一并检查：宽表格仅在自身区域横向滚动，策略矩阵保留可读列宽，长说明换行，小屏统计卡片单列，低高度侧栏可独立滚动。布局源文件为 `page-layout.css`，由 `pack_schemes.py` 嵌入单文件HTML。已覆盖43个页面/页签、320–1920px六种宽度，以及展开策略和输入保持；原独立页面导航与业务流程使用现有脚本回归验证。

## 销售获取与客户策略延期入池（2026年11月17日）

本次按用户补充实现可运行本地账本闭环，新增侧栏“资金池与获取”，下设总资金池、资金获取规则、客户策略与时点、销售入池、期间结算、入池与划拨流水。沿用当前目录与单文件入口，不新建另一套原型。

同一客户可增加多条返利策略，分别配置来源池、比例、月/季/年末时点及是否预留；各策略各期间独立核验，不因月返释放而提前放出年返。支持多个经营来源池，初始来源及上限、比例/按数量/单笔阶梯获取、即时/月/季/年末入池；客户商业政策绑定来源、固定返利/累计阶梯、返利释放时点和是否提前预留。年返先记录权益，年末核验及业务、财务审批后转入客户返利专属池，再登记现金或货款抵扣。转池不新增公司来源，付款不重扣总池。客户、政策和活动方案有资金配置关联入口；审核工作台及结算与清偿承接期间审批和返利发放。19类策略测算不重复生成返利。

建议演示：

1. 用“财务复核”查看/配置总池、获取规则与客户资金时点；新池保存后需启用，默认年返为年末、先记录。
2. 切回“销售申请人”，到“销售入池”登记客户A签收10万元。默认总池获取1万元，服务预留3000元；年返权益本次2000元，加明确承接期初后合计4000元，年内不入客户返利池。
3. 到“期间结算”，模拟业务日改为2026-12-31，发起年返核验；切换业务及财务角色分别通过。4000元转入A返利池，已锁期初2000元解除，总池可用为8000元。
4. 在“结算与清偿”登记返利1000元及唯一财务流水号：客户返利池剩3000元，总池仍8000元。资金流水和客户台账可追溯。

原演示期初仅迁移一次，不重复增加来源；原有活动、政策、试算与清偿记录保留。相同销售行拦截重复；退货继承原快照；规则改版不重算历史；待审明细变化拦截批准但可驳回重报；年返来源不足保留应享；转池后应享减少暂停继续发放，待冲销/追偿，不自动抹账。共享来源余额不能跨客户汇总。

实现：`funding-engine.js`、`funding-ui.js`、`funding-events.js`、`funding-links.js`，由 `pack_schemes.py` 嵌入 HTML。验证：`qa_funding.mjs`、`qa_funding_edges.mjs`、`qa_funding_ui.mjs` 及原有7组回归脚本。当前是浏览器本地持久账本，未连接OMS、ERP、银行、库存或真实OA，未自动执行关账、追偿冲销及全部19类策略资格判断。模拟业务日只用于评审演示。

## 客户活动策略整合

整合用户提供的 `C:/Users/admin/Documents/New project/dealer-strategies.html`，原文件保持不变，参考副本位于 `99-附件与参考/客户活动策略-整合参考.html`。原型采用同一客户和同一账本，不使用 iframe 或另建余额。

业务层级为：客户 → 商业政策版本 → 客户活动方案 → 19 类策略快照 → 费用试算与方案审批 → 执行单据 → 预算审批、核销、结算清偿 → 客户贡献与受益台账。客户及商业政策详情均增加业务关联入口；侧栏“客户活动策略”提供方案列表和策略库。

19 类业务为：采购返利、进货折扣、回款奖励、动销奖励、市场补贴、满额减免、买赠满赠、组合采购优惠、采购增长奖励、连续采购奖励、年度目标奖励、运费补贴、新品试销支持、库存价保调换、陈列奖励、经销商推荐奖励、沉默激活、合同扣点、年返。每项保留源规则、结构化参数、独立测算输入、税口径与执行阶段，并可内嵌到活动方案。

已生效方案保存修改为候选版本，中心池负责人、财务及业务复核全部通过后替换执行版本；原版、策略快照及审批记录保留。方案本身不注入预算，市场费用执行仍由原组织池授权；额度上限同时校验方案和实际账户。规则库更新不回改历史方案，已保存试算保留引用方案版本。

边界：组合报价仅对折扣、满减、激活减免、运费执行单笔顺序叠加或择优，其余业务使用各自输入和期间独立测算，不将所有奖励相加当作应付。跨方案命中、历史已领、客户资质、库存和真实 OA 未自动核验。价格经 OMS 成交价承接；返利走客户预留；实物需库存成本及凭证；合同扣点独立处理。当前自动串联的执行链为市场费用申请、审批占用、核销释放与清偿；其余类型提供规则与对应业务入口，不冒充已完成真实交付。

实现源文件为 `dealer-catalog.js`、`dealer-integration.js`，统一由 `pack_schemes.py` 嵌入 HTML。`qa_dealer.mjs` 验证规则覆盖、快照、方案变更审批和市场执行链。
