# UI 设计理论手册

> 用途：用于产品 UI 设计、作品集叙事、设计评审与研发交付。核心原则是：先让用户理解并完成任务，再追求风格与装饰。

## 1. UI 设计的本质

UI 不是“把页面做漂亮”，而是把用户的目标、产品规则和系统状态，转化成用户能快速理解并顺利完成的界面。

一个好界面通常同时回答五个问题：

1. 我现在在哪里？
2. 我可以做什么？
3. 哪件事最重要？
4. 做完后发生了什么？
5. 出错时怎样恢复？

设计时可用下面的公式自检：

`体验质量 = 目标清晰度 × 操作可理解性 × 状态反馈 × 一致性`

任何一项接近 0，整体体验都会明显下降。

## 2. 先定义问题，再画界面

开始设计前，先写一份极简设计定义：

| 要素 | 需要回答的问题 | 示例 |
| --- | --- | --- |
| 用户目标 | 用户此刻想完成什么？ | 快速找到一位可聊天的 AI 角色 |
| 主动作 | 页面最希望用户做什么？ | 选择角色并发起首次对话 |
| 场景 | 用户何时、何地、带着什么限制使用？ | 碎片时间、首次使用、不了解角色差异 |
| 成功标准 | 什么行为说明方案有效？ | 首次私聊发起率、完成率、任务耗时 |
| 约束 | 业务、技术、内容或合规限制是什么？ | 角色信息不能过长；推荐数据异步加载 |

如果主动作没有被定义，页面往往会出现多个同等醒目的按钮、过多装饰模块，或“看起来丰富但不知道怎么开始”的问题。

## 3. 信息层级：让用户先看到最重要的事

信息层级决定阅读顺序。常用优先级可分为：

- **一级信息**：当前目标、主标题、主操作、关键状态。
- **二级信息**：帮助用户决策的说明、筛选、摘要、次操作。
- **三级信息**：补充说明、历史记录、品牌装饰、低频设置。

建立层级主要依靠位置、大小、对比、留白与分组，而不只是靠颜色。

### 实例：表单页

不佳：标题、说明、十个字段、帮助链接和“保存草稿/提交”两个按钮都同样突出。

更佳：

1. 标题说明这一步的任务。
2. 将字段按用户认知分组，例如“基本信息”“联系方式”。
3. 用说明文字提前解释限制，例如“昵称 2–16 个字符”。
4. 提交按钮作为唯一高强调操作；保存草稿退为次级操作。
5. 出错后将错误定位到字段旁，并保留用户已填写的内容。

## 4. 可见性、匹配与认知负荷

### 4.1 让系统状态可见

用户点击、提交、等待、成功或失败时，系统必须给出与动作匹配的反馈。

| 状态 | 合适反馈 | 不佳做法 |
| --- | --- | --- |
| 加载 | 骨架屏、进度、按钮 loading | 页面静止，用户不断点击 |
| 成功 | 明确成功信息 + 下一步 | 只弹出短暂 Toast，用户不知道数据是否真的保存 |
| 失败 | 原因、恢复办法、重试入口 | 只显示“操作失败” |
| 空状态 | 为什么为空 + 可以采取的动作 | 留一大片空白 |

### 4.2 使用用户熟悉的语言

界面应贴近用户任务和业务语言，而不是内部系统术语。

例如：面对教师使用的后台，写“查看待跟进学生”通常比写“风险对象数据洞察”更清晰；“清除筛选”也比单独一个难以理解的图标更安全。

### 4.3 降低一次需要记住的内容

优先让用户“看见并识别”，而不是“回忆”。常用方法：

- 将复杂任务拆成连续的小决策，而非一次塞进长表单。
- 已选筛选条件保留在界面上，提供数量与清除入口。
- 对低频复杂功能提供示例、默认值或最近使用记录。
- 重要操作放在发生上下文附近，而不是要求用户跳转寻找。

## 5. 交互设计：每个组件都应有完整状态

组件不是一张静态图，而是一套可重复使用的行为规则。设计高频组件时，至少检查：

`默认 → 悬停/聚焦 → 按下 → 已选 → 禁用 → 加载 → 空 → 成功/错误`

不同组件取适用状态，不必机械地全部出现，但不能只设计“正常时”。

### 实例：筛选组件

| 场景 | 推荐设计 |
| --- | --- |
| 默认 | 显示筛选名称与展开箭头 |
| 已选 | 显示已选数量或关键标签；允许一键清除 |
| 无结果 | 说明“没有符合条件的结果”，提供清除筛选 |
| 加载 | 保留当前选择，显示局部 loading，避免整页跳动 |
| 超长文本 | 限制单行、截断并提供完整内容提示 |
| 禁用 | 降低强调但保持文字可读；说明禁用原因（如有必要） |

## 6. 视觉系统：一致性比“每页都不同”更重要

### 6.1 色彩

色彩承担品牌、层级和语义三类工作：

- **品牌色**：主要操作、关键强调。
- **中性色**：正文、边界、背景、分区。
- **语义色**：成功、警告、错误、信息。

不要只用颜色表达状态。例如错误字段除了红色，还需要错误文案、图标或字段边界变化。普通正文建议达到至少 `4.5:1` 对比度；大字号文字至少 `3:1`。

### 6.2 字体与排版

- 同一页面保持有限的字号等级，通常用标题、区块标题、正文、辅助文案四级即可。
- 正文行距要让连续阅读轻松；信息密集表格可稍紧，但不能以牺牲可读性换空间。
- 数字、时间、金额等关键信息应使用稳定的对齐方式，便于比较。
- 不要依赖全大写、超细字重或极浅灰文字表达重要信息。

### 6.3 间距、圆角与阴影

将常见间距收敛为一组 token，例如 4、8、12、16、24、32。相同关系使用相同间距：同组内容更近，不同组内容更远。

圆角、描边和阴影需要表达层级：卡片浮在页面上、弹窗高于卡片、输入框处于可编辑状态。阴影不应仅用于装饰。

## 7. 动效：解释变化，不打断任务

好的动效只服务于五件事：进入、位置变化、加载、完成和错误。

- 页面或模块进入：帮助建立内容关系，不要让用户等待很久。
- 列表更新：保持用户对“哪些内容变了”的理解。
- 提交加载：阻止重复操作，说明系统正在处理。
- 成功反馈：确认完成，并指出下一步。
- 错误反馈：帮助定位问题，不用晃动整页制造焦虑。

动效应支持减少动态效果的偏好；非必要动效应可跳过，不能延迟核心任务。

## 8. 数据与结果：让设计价值可信

作品集与项目复盘中的数字，应至少说明口径，而非单独展示一个涨幅。

推荐句式：

`指标 A：4.2 → 7.5；灰度上线后 14 天；登录用户；数据来自埋点后台；与标签排序改造共同作用。`

如果不能披露具体数字，不编造数字。可写：

`通过灰度观察卡片浏览与下一步点击，浏览深度相较旧版呈提升趋势；该指标作为后续迭代依据。`

设计结果要区分：

- **产出**：做了多少页面、组件或规范。
- **可用性结果**：用户是否完成任务、是否减少错误或耗时。
- **业务结果**：转化、留存、使用深度等变化。
- **归因边界**：结果可能受产品策略、运营、算法、季节性等共同影响。

## 9. 无障碍与包容性

无障碍不是最后补的检查项。至少保证：

- 文字与背景有足够对比，不只用颜色传达状态。
- 键盘可以访问主要操作，焦点位置清晰可见。
- 图标按钮有名称或文本提示。
- 表单错误能被清楚读到，并指出如何修复。
- 点击区域足够大，移动端避免把关键操作做得过小。
- 动效不会造成眩晕或阻碍阅读。

## 10. 设计评审清单

每次评审可按以下顺序检查：

1. 用户目标和主操作是否明确？
2. 首屏能否在几秒内说明“这是什么、可以做什么”？
3. 信息层级是否只有一个合理的重点？
4. 组件是否复用现有模式，并覆盖必要状态？
5. 加载、空、成功、失败和异常数据怎么处理？
6. 颜色、字号、间距、圆角和阴影是否一致且可读？
7. 文案是否描述用户能理解的动作和结果？
8. 动效是否解释变化、支持减少动态效果？
9. 是否考虑键盘、对比度、图标说明和触达区域？
10. 方案是否可被研发交付、可被数据验证、可被后续维护？

## 11. 作品集表达模板

每个案例可用以下顺序组织：

1. **项目速览**：背景、目标、用户、角色、约束、结果。
2. **问题与证据**：旧流程、数据、访谈或业务限制。
3. **洞察与原则**：从证据推导出的设计判断。
4. **关键方案**：只讲最能说明决策的流程、页面和组件。
5. **交付与协作**：规范、状态、研发走查、迭代方式。
6. **验证与复盘**：指标口径、用户反馈、下一轮优化。

用“我解决了什么问题、为什么这样设计、如何证明有效”替代“我画了哪些页面”。
