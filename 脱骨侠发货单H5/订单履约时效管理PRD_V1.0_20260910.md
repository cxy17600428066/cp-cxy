## 1 产品目标与范围

本产品用于管理订单从提交到回执上传的履约时效，让老板先看总览、再定位异常订单，让业务人员按节点跟进。普通客户使用商品及节点时效；大型连锁商超等系统客户依据每笔订单的客户要求到货时间安排各节点截止时间。

本期保留“总览指标—履约节点—下方订单明细”的操作方式。商品时效、履约节点和客户到货配置分别独立成页，不将配置嵌入订单详情，不重做现有订单中心、财务审核或仓储执行系统。

### 1 1 业务目标

- 统一发货、揽收、签收和回执的时间口径，避免各系统以不同状态统计同一环节。
- 支持财务审核与工厂接单并行计时，同一订单总数去重，节点待办分别统计。
- 区分普通客户和系统客户，避免客户约定交期被通用时效覆盖。
- 缺少时间或履约证据时提示待补充或待判定，不将未知状态显示为正常或直接判为超时。
- 保留现有订单资料展示，同时提供订单号、客户和下单日期查询。

### 1 2 本期信息架构

| 菜单分组 | 页面 | 核心用途 |
| --- | --- | --- |
| 订单管理 | 订单列表 | 查询订单 经销或KA下单 订单详情 |
| 订单管理 | 履约总览 | 全部订单与系统客户总览 节点切换 异常定位 |
| 时效设置 | 商品时效配置 | 展示标准库有货和无货时效 配置特殊商品方案 |
| 时效设置 | 履约节点配置 | 配置六个节点的完成时限和提醒策略 |
| 时效设置 | 客户到货配置 | 设置系统客户默认规则及客户专属规则 |

### 1 3 角色与边界

老板或管理人员以查看总览和订单详情为主；业务人员负责下单、核对客户交期并跟进异常；财务、工厂、仓储人员在各自业务系统完成操作；配置管理员维护时效规则。正式权限划分及数据范围属于上线前设计要求，当前原型未实现登录与角色授权。

本期不包含独立的“物流信息获取”履约节点、司机与车辆配置菜单、商品全局默认时效编辑、客户期望卸货时间。物流轨迹仍可作为订单资料和签收证据的数据来源，但不是额外的计时节点。旺店通收集司机和车牌信息的能力留待后续评估，不作为本期依赖。

文中的“已确认”指业务已明确的流程与页面要求；“原型现状”描述当前前端能力；“建议”及第12章的待确认项需评审后定版。当前页面可操作不代表已接入真实订单、ERP、WMS或消息服务。

## 2 履约流程与节点定义

### 2 1 主流程

订单提交后，财务审核与工厂接单同时开始，各自完成、各自停止计时。工厂接单不得等待财务审核通过才启动。

后续依次关注同步旺店通、ERP同步WMS并生成快递单号、WMS出库、实际签收、回执上传。财务和接单是否必须均完成后才允许同步旺店通，尚未确定，见D02。

### 2 2 六个计时节点

| 节点 | 起算事件 | 完成事件 | 统计说明 |
| --- | --- | --- | --- |
| 财务审核 | 订单提交成功 | 财务审核通过 | 与工厂接单并行 |
| 工厂接单 | 订单提交成功 | 工厂接单完成 | 不以财务审核通过为起点 |
| 发货 | 同步旺店通成功 | ERP同步WMS成功且生成快递单号 | 两项均满足才算发货 |
| 揽收 | WMS收到ERP订单 | WMS出库完成 | 以出库作为揽收维度 |
| 签收 | WMS出库完成 | 客户实际收到货并签收 | 不能用物流查询成功代替签收 |
| 回执上传 | 客户实际签收 | 回执单上传成功 | 未签收不启动计时 |

发货完成时间取“WMS收单成功时间”与“快递单号生成时间”两者较晚的时间。仅同步成功、仅有快递单号，均不满足完整发货条件。快递单号的实际产生系统及获取字段需在接口评审中确认。

揽收从WMS收单时开始，因此可能先于发货节点的最终结束时间。若快递单号稍后才生成，发货与揽收待办可以短暂并存。系统应按各自事件计时，不能强制把所有节点处理为单一串行状态。

### 2 3 事件及完成原则

- 完成事件一经确认，对应节点停止累计用时；其他未完成节点继续计时。
- “未收到完成记录”与“业务确认尚未完成”必须区分。数据缺失时显示待同步或待判定。
- 原订单资料中的“已发货”等状态仅用于资料展示，不直接替代上述事件时间。
- 事件发生时间用于计算业务时效，接口接收时间用于判断同步延迟，两者分开保存。
- 回执的适用订单范围取决于“是否回执”的最终规则。当前已确认计时起点与终点，但“否”是否跳过任务仍待确认，见D03。
- 分批发货、多包裹、多次签收的订单级完成条件见D04，不能默认以第一条完成记录关闭整单。

## 3 普通客户与商品时效

### 3 1 商品时效来源

商品基础时效在标准库商品管理中维护。本页面只读展示每个商品的“有货发货时效”和“无货发货时效”，不提供全局默认时效编辑。当前原型为未命中自定义方案的商品预填24小时和72小时；正式系统必须读取每个商品实际维护的标准库值，不能把这两个展示值写成全商品统一政策。

单个商品的规则优先级为：已启用的自定义方案优先；未匹配、方案停用或方案删除时，使用标准库商品时效。库存为有货时取有货值，库存为无货时取无货值。库存状态取哪个系统、在哪个时点冻结，见D01。

### 3 2 商品时效明细与筛选

明细列包含商品编码、商品名称、有货发货时效、无货发货时效、时效来源及方案名称。支持商品名称或编码关键词、标准库或自定义来源、有货时效范围、无货时效范围组合筛选。范围包含上下限；最小值不得大于最大值；空条件表示不限。

展示当前筛选数量与商品总数。没有结果时提示调整筛选条件，不显示空白表格。标准库未返回有效时效时，应标注待同步或待维护，不自动推定一个可用于生产判定的时限。

### 3 3 自定义方案

| 字段或操作 | 要求 |
| --- | --- |
| 方案名称 | 必填 同名方案不可重复 原型最多50字 |
| 适用商品 | 支持按名称或编码搜索勾选 支持批量粘贴编码 |
| 选择同步 | 勾选 取消勾选 移除已选项 粘贴编码保持同一份选择结果 |
| 编码处理 | 忽略英文字母大小写 去除空项并去重 单个编码最多80字符 |
| 商品数量 | 一个方案关联1至200个商品 |
| 有货与无货时效 | 分别必填 0.1至8760小时 支持0.1小时精度 |
| 启用状态 | 同一商品只能关联一个已启用方案 冲突阻止保存 |
| 编辑停用删除 | 编辑保留原关联商品 删除需二次确认 停用或删除后回退标准库 |

可以保留未在当前目录中找到的粘贴编码，但不得把它认定为有效标准库商品。正式保存时是否必须验证商品存在性、如何处理已下架商品，随商品接口一并确认。

### 3 4 与订单发货节点的关系

业务已确认普通客户需使用商品时效，并允许特殊商品覆盖标准库。当前总览仍主要按节点固定阈值计算，尚未将商品方案接入真实订单计时引擎。

商品发货时效是否从下单起算，以及它与“同步旺店通成功后到ERP同步WMS并生成单号”的发货节点时限是覆盖关系还是两个独立约束，必须先确定。多商品订单按最长、最短还是逐商品判断，也须明确。以上均列入D01，不应由研发自行假定。

## 4 履约节点配置

### 4 1 页面要求

六个节点固定展示，起止事件清晰可见。每张配置卡主要呈现“从什么事件开始”“多久内完成”“完成什么事件后停止”。财务审核和工厂接单明确标注并行。

常用时限直接编辑；提醒比例与超时处理方式放入可展开区域。配置页独立存在，不放入订单详情。关闭节点提醒只影响预警展示与通知，不改变订单业务流转，不等于完成节点或跳过该环节。

### 4 2 当前预填参数

| 节点 | 完成时限 | 提醒比例 | 提前提醒示例 |
| --- | --- | --- | --- |
| 财务审核 | 2小时 | 80% | 用时达到1.6小时 |
| 工厂接单 | 1小时 | 80% | 用时达到0.8小时 |
| 发货 | 24小时 | 75% | 用时达到18小时 |
| 揽收 | 4小时 | 75% | 用时达到3小时 |
| 签收 | 72小时 | 80% | 用时达到57.6小时 |
| 回执上传 | 24小时 | 80% | 用时达到19.2小时 |

以上为原型预填值，均可修改；生产初始化值需要业务确认。商品展示的24或72小时，与这里的节点阈值不可仅因数值相同就视为同一规则。

### 4 3 校验与保存

节点时限必须为0.1至8760小时内的有效数值。提醒比例为1%至99%，不能为0或100。超时处理方式当前可选“创建异常工单”“仅消息提醒”“消息提醒并升级”。

点击保存后统一校验，错误应指向对应节点和字段，不部分保存。读取异常不得静默覆盖原配置。正式系统应记录配置版本、修改人和修改时间，并防止多人同时编辑覆盖，详见第10章。

本配置主要描述普通节点耗时。系统客户的节点截止由客户到货规则计算，页面和订单详情不得把普通固定小时数显示成系统客户的实际截止规则。

## 5 系统客户到货配置

### 5 1 客户分层与规则优先级

系统客户指下单时提供要求到货时间的大型连锁商超等客户。此类订单使用客户到货倒排规则，不直接套用普通节点时长。非系统客户仍使用商品与普通节点规则；到货时间可选填，但缺失不进入“系统客户到货时间待补充”提醒。

多数系统客户使用一套默认时间，仅特殊客户单独配置。页面保持“默认时间设置”和“客户设置”两部分，试算功能折叠展示。

规则选择顺序为：订单自身已保存的有效规则快照优先；没有快照时，使用客户专属规则；没有专属规则时，使用系统客户默认规则。历史订单没有快照而按当前规则估算时，必须注明来源，不伪称为下单时原规则。

### 5 2 默认倒排参数与计算

| 项目 | 原型预填值 | 截止时间计算 |
| --- | --- | --- |
| 财务审核 | 到货前72小时 | 要求到货时间减财务提前量 |
| 工厂接单 | 到货前60小时 | 要求到货时间减接单提前量 |
| 发货 | 到货前48小时 | 要求到货时间减发货提前量 |
| 揽收 | 到货前36小时 | 要求到货时间减揽收提前量 |
| 签收 | 要求到货时刻 | 等于客户要求到货时间 |
| 回执上传 | 实际签收后24小时 | 实际签收时间加回执时限 |
| 提前提醒 | 截止前2小时 | 节点截止时间减提醒时长 |
| 超时升级 | 截止后2小时 | 节点截止时间加升级时长 |

财务与接单提前量各自设置，不限制两者谁先谁后；两者均不得小于发货提前量，发货提前量不得小于揽收提前量。该校验约束的是计划日期，不代表财务必须先于接单。时间范围为0至8760小时，当前表单步长0.5小时；回执和升级时长必须大于0。

### 5 3 客户资料与异常处理

客户编码、名称必填；编码忽略大小写后唯一。当前原型要求名称唯一以匹配订单，正式系统应使用客户ID或编码关联，同名客户如何区分由客户档案能力决定。系统名称随档案带出，客户类型只能为系统或非系统。

选择系统客户专属规则时允许编辑；选择默认规则时只读展示继承结果；非系统客户不展示可生效的倒排参数。系统客户缺少到货时间时提示待补充，规则无效时提示待检查，均不得回退成普通24小时或72小时判定。

## 6 系统客户计算示例与交期变更

### 6 1 倒排示例

客户要求2026年9月18日10时到货，使用第5章的预填参数，得到以下计划。示例仅解释计算方法，不代表实际订单或最终生产参数。

| 节点 | 计划最晚完成时间 | 提醒时间 |
| --- | --- | --- |
| 财务审核 | 9月15日10时 | 9月15日8时 |
| 工厂接单 | 9月15日22时 | 9月15日20时 |
| 发货 | 9月16日10时 | 9月16日8时 |
| 揽收 | 9月16日22时 | 9月16日20时 |
| 签收 | 9月18日10时 | 9月18日8时 |
| 回执上传 | 若9月18日9时30分签收 则9月19日9时30分截止 | 截止前2小时 |

回执只在取得实际签收时间后计算，不能按要求到货时间加24小时替代。回执提醒不得早于其实际起算时间。

### 6 2 下单时的交期检查

系统客户必须填写客户要求到货时间。新建订单填写的到货时间应晚于当前时间。普通客户选填；一旦填写也应进行合法性校验。

若某个倒排节点在下单时已过计划截止，应明确列出风险节点及时间。当前原型允许风险确认后保存草稿，不代表正式系统允许直接提交或自动承诺该交期。正式提交是阻止、审批还是允许带风险继续，见D06。

### 6 3 规则与交期变更

首次保存草稿时保留客户类型、适用规则和计算依据。重新打开不应因默认规则修改而悄悄改变草稿时限。已有订单若有有效系统规则快照，即使客户档案后来改为非系统或删除，也应保留订单原规则来源。

修改已保存的客户要求到货时间必须填写修改原因，并记录原值、新值、修改时间及操作者。当前原型的操作者只是本机占位信息，正式系统必须取登录用户。

对正式订单变更交期后，已完成节点是否追溯、未完成节点是否重算、已发预警是否撤销，尚待确定，见D05。不得通过静默修改交期清除历史违约记录。

## 7 履约总览

### 7 1 展示与切换

保持顶部客户范围切换、中间总览指标及六个节点卡片、下方订单明细的结构。点击指标或节点，仅更新下方对应订单，不额外跳转详情页，也不把完整订单卡片替换为难以阅读的密集摘要。

全部订单视图显示履约中、已超时、即将超时、正常四个主指标，并补充今日要求到货、系统客户到货时间待补充、到货超时及必要的待判定提醒。系统客户视图显示系统订单数、到货超时、今日要求到货、到货时间待补充，节点超时与预警作为补充入口。

### 7 2 核心统计口径

| 指标 | 口径 |
| --- | --- |
| 履约中订单 | 至少存在一个适用待办节点的订单 按订单ID去重 |
| 节点待完成数量 | 该节点尚未完成的订单数 一单可出现在多个节点 |
| 订单时效状态 | 待办中优先展示超时 再预警 再待判定 再正常 最后提醒关闭 |
| 今日要求到货 | 按北京时间自然日比较要求到货日期 不是下单日期 |
| 到货时间待补充 | 仅系统客户且缺少有效要求到货时间的订单 |
| 到货超时 | 区分明确未签且已过交期 与已签但实际签收晚于交期 |
| 订单金额 | 汇总当前展示订单的应付金额 按订单去重 不是实付金额 |

当前仍有回执待办的已签收订单可能继续出现在履约中总览，因此“到货超时”下须明确区分“到货已超时”和“超期签收”。不要把历史超期签收当作仍未送达。取消、退换、作废的统计纳入规则见D07。

### 7 3 节点卡片与视觉

六个节点使用一致卡片结构，财务与接单标注并行。显示待完成数量、正常、预警、超时，必要时补充待判定。总订单数不能简单相加节点数量。

普通订单显示固定节点时效；系统客户前五个节点注明按客户要求到货时间倒排，回执注明签收后按客户规则计时。红色表示超时，橙色表示预警，绿色表示正常，灰色表示待判定、待同步或关闭；状态同时有文字，不能只靠颜色区分。

## 8 订单查询与详情

### 8 1 查询条件

订单列表和履约总览下方明细均提供订单号、客户名称、下单开始日期、下单结束日期。订单号和客户名称采用关键词匹配，多个条件同时满足才展示。日期包含起止当天，按北京时间计算。

开始日期不得晚于结束日期；只填一端时视为单边范围；日期均为空时不限日期。填写日期条件而订单缺少有效下单时间时，不将其误判为符合条件。清空查询恢复四个查询字段，不隐式修改业务数据。

列表查询只影响下方订单，不改变上方总览统计，页面须明确提示。当前节点、时效状态和查询条件叠加生效；无结果时说明没有符合条件的订单并提供调整或清空入口。

### 8 2 订单资料展示

| 信息区 | 主要字段 |
| --- | --- |
| 订单头 | 订单编号 下单时间 来源 类型 创建人 当前节点 剩余或超时时长 |
| 商品 | 商品名称 编码 规格标签 单价 数量 单位 搭赠数量 |
| 金额 | 订单应付金额 当前列表金额合计 |
| 收货 | 收货人 手机 收货区域与地址 |
| 客户 | 客户名称 所属系统 销售人员 系统客户标识 |
| 状态 | 原订单状态 审核或接单等资料状态 本产品的时效状态 |
| 补充信息 | 工厂备注 客户要求到货时间 到货状态 负责人如有 |
| 操作 | 查看订单详情 |

金额以导入或接口中的应付金额为准，不因名称含“订单金额”就改称实付。原始资料状态与本产品节点时效分开展示。界面隐藏“演示默认”“资料来自某文件”等说明性字段，但不得由此把演示用时当成正式事件证据。

### 8 3 系统客户与并行待办

系统客户订单显示客户要求到货时间、本节点最晚完成时间和规则来源。缺资料时显示具体原因，如到货时间待补充、履约记录待同步、客户配置待检查。

同单有多个待办时应展示全部当前待办。用户从工厂接单节点打开订单，详情应定位工厂接单，不得错误定位到该订单的财务待办。

列表优先超时、预警、待判定，再正常。相同时效状态下，系统客户按实际节点截止时间排序，不用通用小时数替代；普通客户按超时或剩余程度排序。数据不完整的订单不得被合并进“正常履约”以掩盖未知待办。

## 9 经销与KA下单

### 9 1 入口与基础表单

从订单列表的“经销/KA下单”进入右侧新增抽屉，保持现有OMS蓝白风格。标题、底部保存和取消按钮固定，表单内容可滚动。下单字段与现有业务资料一致，使用“客户要求到货时间”，不再使用“最晚发货时间”。

| 字段 | 必填或行为 |
| --- | --- |
| 客户名称 | 必填 选择已配置客户 未匹配时提示维护客户 |
| 系统名称与客户类型 | 由客户资料带出 系统名称只读 |
| 是否仓库收货 | 是或否 |
| 收货人员 手机号码 | 必填 正式手机格式校验需业务约定 |
| 收货区域 收货地址 | 必填 |
| 客户要求到货时间 | 系统客户必填 非系统客户选填 |
| 特殊备注 | 最多500字 |
| 经销转私域 是否换货下单 | 是或否 |
| 是否回执 | 是或否 默认否 已替换是否团购 |
| 发货主体 | 卓希工厂或运营中心 |
| 特殊情况说明 | 展示匹配规则或相关说明 |
| 备注 | 最多1024字 |

已删除客户期望卸货时间的起止输入及校验。旧草稿中的团购值不得迁移为是否回执；旧卸货字段不再回填，重新保存时不带入新表单。

### 9 2 商品清单与保存

至少添加一件商品。清单展示商品名称、单位、口味、红线价、售价、数量、搭赠数量、搭赠比例和总数量；未接入的资料不得捏造。数量为正整数，搭赠数量为非负整数，售价为非负数，金额按价格精度展示。

系统客户下单时可查看节点截止与预警时间。已保存交期变更必须填原因，见第6章。“是否回执”须独立保存与回填，但它对任务创建、总览统计和提醒的影响仍见D03。

当前原型只保存本机单份草稿，不创建真实订单。正式对接时，应区分保存草稿与提交订单，并在提交成功后取得真实订单ID，才能进入履约任务和总览统计。提交失败须保留输入并允许重试；重复点击不得生成重复订单。

## 10 预警判定与系统对接

### 10 1 预警计算

普通节点截止时间等于实际起算时间加配置时限；提醒时间等于起算时间加“配置时限乘提醒比例”。系统客户以倒排得到的节点截止时间为准，提醒时间等于截止时间减客户配置的提前提醒时长。回执统一从实际签收开始。

对已明确未完成的节点：当前时间早于提醒点为正常，达到提醒点且早于截止为预警，达到截止仍未完成为超时。已完成节点按实际完成时间比较截止，不再随当前时间增长。完成时间恰好等于截止视为按时。

缺少起算事件、客户交期、有效规则或明确的完成状态时显示待判定，并标注缺少内容。接口字段缺失表示未知，不能自动当作明确未完成；系统间具体字段约定须包含该语义。

### 10 2 集成事件与责任边界

以下是逻辑事件清单，不代表外部系统已经提供对应接口。研发须核实来源系统、字段名称、回调或轮询方式、失败重试和时间精度。

| 事件或数据 | 预期来源 | 用途 |
| --- | --- | --- |
| 订单提交 客户与商品资料 | OMS或现有订单服务 | 创建订单及财务接单待办 |
| 财务审核通过 工厂接单完成 | 对应审核或接单服务 | 结束并行节点 |
| 同步旺店通成功 | 旺店通同步链路 | 启动发货节点 |
| WMS收单成功 快递单号生成 | ERP WMS及单号生成系统 | 完成发货 启动揽收 |
| 出库完成 | WMS | 完成揽收 启动签收 |
| 客户实际签收 | 物流签收回传或经确认的收货记录 | 完成签收 启动适用回执任务 |
| 回执上传成功 | 回执业务服务或文件服务 | 结束回执计时 |
| SKU有货无货时效及库存口径 | 标准库及库存服务 | 选择普通商品时效 |

签收证据不能由“无物流消息超过某时长”自动代替。无物流信息时如何取得人工签收证据、由谁确认，见D08。接口是否可获取司机和车牌不影响本期六节点计时。

### 10 3 消息与异常动作

原型提供提醒方式选项，未真正发送消息或创建工单。正式实现建议按订单、节点、规则版本和告警等级去重，避免每次刷新或重复回调反复通知。收件人、渠道、重复提醒间隔、升级对象和处置闭环须与D08一起确认。

## 11 数据设计与上线要求

### 11 1 建议数据对象

| 对象 | 关键内容 |
| --- | --- |
| 订单 | 订单ID 客户ID 客户类型 要求到货时间 是否回执 下单时间 |
| 商品明细 | SKU 数量 单位 金额 时效来源 有货或无货口径 |
| 商品自定义方案 | 方案ID 版本 名称 关联SKU 有货时效 无货时效 启用状态 |
| 节点规则 | 节点编码 起止事件 时限 提醒比例 提醒开关 处理动作 |
| 客户规则 | 默认或专属 倒排提前量 回执时长 提醒及升级时长 |
| 订单规则快照 | 生效版本 客户类型 选用规则 原值与来源 保存时间 |
| 节点任务 | 订单或履约单ID 节点 起算 截止 提醒 完成时间 当前状态 |
| 原始事件 | 来源事件ID 业务发生时间 接收时间 原始状态 处理结果 |
| 告警与变更记录 | 触发原因 处置记录 交期前后值 修改原因 操作者 时间 |

正式系统用稳定的客户ID或编码关联订单，不依赖客户名称文本。原型的单份本地草稿和浏览器配置存储不作为正式数据模型。

### 11 2 可靠性与审计要求

建议为事件同步建立幂等处理与失败重试。乱序事件按业务发生时间归并；补传或纠正事件应保留原记录，重算受影响任务并留痕。不得重复生成节点待办、重复发送同级提醒或重复增加总览数量。

规则保存采用版本控制或等效的并发校验。编辑冲突给出明确提示，不能后保存者无声覆盖前一版本。历史订单的快照和交期修改记录应可追溯，配置删除不能让历史订单失去解释依据。

所有页面统一使用北京时间展示，后台建议保存可明确时区的时间值。自然小时、工作小时、节假日及截止边界的正式日历策略见D07，不将浏览器设备时间作为可信判定时钟。

### 11 3 权限与文件安全

正式系统应接入现有登录与权限体系。查看、配置、下单、修改交期、确认签收和回执上传分别授权；收货电话、地址等信息按业务权限可见。操作者必须取真实登录身份，不允许由前端任意填写。

回执文件的类型、大小、份数、有效性复核及保留期限见D03。文件下载应鉴权，上传失败不停止计时，重复上传或替换需留记录。安全检查和存储策略由正式文件服务实现。

数据规模、查询响应时间、同步延迟目标、可用性和备份恢复目标应在接口与上线评审中量化，不以当前少量原型数据的运行速度作为验收承诺。

## 12 上线前待确认事项

以下问题影响正式统计或流程，不属于研发可自行选择的界面细节。

### D01 商品时效与发货节点衔接

确定商品发货时效的起算点；标准库和商品方案值是覆盖发货节点时限，还是与系统同步耗时并列约束。明确库存取值来源和冻结时点、多SKU时效如何聚合、商品编码不在标准库时是否允许保存。

### D02 并行审核后的业务门槛

财务审核和工厂接单各自计时已确认。仍需确定同步旺店通是否要求两者都完成，审核驳回、接单拒绝、重新提交和撤回时如何处理原任务及原计时。

### D03 回执适用范围与有效文件

确认“是否回执＝否”是否不创建回执任务、不计入待办和告警；“是”是否必须完成回执才算整单履约完成。同步确定默认值、订单创建后是否允许修改，以及回执文件验收标准。当前原型只保存该字段，尚未联动跳过任务。

### D04 分批履约与订单级完成

明确一单多发货单、多包裹、部分出库、部分签收时，以首次、全部完成还是逐履约单计时。确认未发剩余商品、补发、少收及分批回执如何保留待办。建议保留订单总览去重与履约单明细两层，但需业务定版。

### D05 规则生效与交期变更

明确配置仅影响新单还是允许选择历史未完成订单重算；修改交期是否需审批；已完成节点、已发告警和历史超期记录是否保留。既有有效快照不得被新规则无声覆盖。

### D06 交期风险与正式提交

若要求到货时间已过、下单时某节点倒排截止已过，正式下单应阻止、审批还是带风险放行。确认允许操作的角色及交期重新协商流程，不沿用“能保存草稿”等同“能提交订单”的假设。

### D07 日历与统计排除条件

确认按连续自然小时还是工作时间计时，是否包含节假日。明确取消、作废、退款、退换及暂停订单是否排除、冻结或继续统计，以及恢复后的起算方式。

### D08 签收证据及通知闭环

确认无物流信息订单由谁确认实际签收、采用何种凭证及复核方式。确定消息渠道、节点责任人、升级对象、重复提醒间隔、工单关闭条件和外部接口可提供的实际字段。

以上事项应由业务负责人牵头，结合财务、工厂、仓储、客服及研发完成评审。文档不代填审批结论或负责人姓名；未定版的关键口径不应进入生产验收。

## 13 功能验收标准

下列场景用于联调与测试。涉及D01至D08的用例，应先补齐业务结论，再执行最终验收。

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| A01 | 同单提交后财务与接单均未完成 | 两个节点各计1待办 总订单只计1 |
| A02 | 只完成财务审核 | 财务停止计时 接单继续计时 不重置起点 |
| A03 | 只有WMS收单或只有快递单号 | 均不单独认定发货完成 两项满足后取较晚时间 |
| A04 | WMS出库完成 | 同时结束揽收并启动签收 不等待物流首次扫描 |
| A05 | 未签收或回执上传失败 | 未签收不启动回执 上传失败不结束已启动计时 |
| A06 | 普通节点2小时 提醒80% | 1.59小时正常 1.6小时预警 2小时仍未完成即超时 |
| A07 | 系统客户默认与专属规则 | 专属覆盖默认 按客户交期倒排 不套普通固定时长 |
| A08 | 普通客户缺少到货时间 | 不进入系统客户到货时间待补充统计 |
| A09 | 系统客户缺交期或履约证据 | 显示具体待补或待判定原因 不伪造截止或完成状态 |
| A10 | 财务正常但并行接单待判定 | 整单不得显示为全部正常 未知待办仍可见 |
| A11 | 搜索勾选及批量粘贴SKU | 选择结果一致 去重 大小写等价 取消与移除同步 |
| A12 | 同一SKU归属两个启用方案 | 阻止保存并指出冲突 不破坏原配置 |
| A13 | 停用或删除商品方案 | 该商品按标准库时效解析 历史快照仍可解释 |
| A14 | 财务与接单提前量互换 | 允许独立先后 但二者均不得计划晚于发货 |
| A15 | 改已保存的要求到货时间 | 必填原因 保留前值后值时间及真实操作者 |
| A16 | 修改客户类型或删除客户档案 | 有效订单规则快照继续生效 不无声切换为普通客户 |
| A17 | 订单号客户日期组合查询 | 多条件同时匹配 日期含结束当天 清空有效 |
| A18 | 总览指标或节点切换 | 下方订单同步变化 查询不改变上方总览统计 |
| A19 | 从接单节点打开并行订单 | 详情定位接单 系统客户展示该节点实际截止 |
| A20 | 新下单字段与旧草稿 | 无卸货时间 是否回执可保存回填 不读取旧团购值 |
| A21 | 相同状态的系统客户订单排序 | 更早到期或超时更久者优先 不按通用时长排序 |
| A22 | 重复回调及提交重试 | 不重复创建订单任务或提醒 总览数量不重复增加 |

验收同时核对列表数量、应付金额合计与筛选结果。完成节点必须停止计时，临界时刻与时区结果一致，缺失数据有明确提示。真实消息、工单和文件上传必须通过实际链路验证，不能以按钮可点击代替。

## 14 原型边界与实施建议

### 14 1 当前已具备的前端能力

现有页面已包含独立导航、总览与明细联动、系统客户视图、订单查询、六节点配置、商品时效明细、自定义方案勾选与粘贴、客户默认及专属规则、倒排试算、下单抽屉、本地草稿、规则快照与交期修改记录。

订单资料使用已有表格数据展示，履约节点与用时仍包含原型展示设置。业务界面已隐藏演示说明，但这些值不能作为真实事件、实际经营结果或生产SLA达成情况。

### 14 2 正式系统尚需完成

- 后端订单提交、配置持久化、权限、真实操作者审计及多端共享。
- 标准库商品和库存接口，以及商品方案到订单时效引擎的真实联动。
- 旺店通、ERP、WMS、物流、实际签收及回执上传的数据接口。
- 事件驱动的节点任务、告警发送、异常工单及升级闭环。
- 客户稳定ID关联、规则版本与历史快照、分批履约和异常重算。
- “是否回执”对适用任务、整单完成、总览及提醒的联动。

### 14 3 建议实施顺序

先确认第12章的关键业务口径和事件来源，再定稿数据模型、规则版本及接口契约。优先打通财务和接单并行、发货双条件、出库与签收及回执事件；随后接入客户倒排和商品时效计算，并核对总览去重与状态判定。

在数据链路稳定后接入消息、工单、升级、权限和文件能力，按第13章完成正常、异常、临界时刻和重试场景验收。具体排期、投入和性能目标由研发评估后确定，本文件不预设承诺日期。

### 14 4 评审交付清单

业务评审需给出D01至D08的结论；接口评审需确认各节点事件及权威时间字段；技术设计需明确规则快照、任务状态和异常处理；测试需维护用例与证据；上线需确认配置初始化、历史数据处理、通知接收人、权限及故障处理方案。
